# PaperScout Wiki 渐进式加载与 Ingest 方案

> 状态：当前已确认的设计方案。本文记录产品和流程决策，不表示相关代码已经完成。

## 1. 项目目标

用户可以收集一篇或多篇论文，由 QA Agent 读取 Wiki，理解论文内容并回答问题。系统支持三类使用场景：

- **领域概览**：读取多篇论文，生成简短综述。
- **方法比较**：比较不同论文使用的方法、步骤或模块。
- **研究构思**：讨论模块组合，以及借鉴其他领域方法的可能性。

Wiki 内容以研究问题和方法理解为重点。研究构思属于待验证的建议，引用已有论文不能直接证明组合方案有效或具有新颖性。

## 2. 每篇论文的 Wiki 内容

每篇论文保存一份 Wiki，包含以下五部分：

| 内容 | 保存要求 |
| --- | --- |
| **研究问题** | 论文研究什么任务、解决什么问题 |
| **核心思路** | 论文整体使用什么思路解决问题，保留关键技术特征 |
| **方法** | 主要步骤或组成部分，以及各部分如何连接 |
| **实验概况** | 做了哪些实验、验证什么问题、使用哪些评估指标 |
| **结论与局限** | 作者总结，以及明确报告的局限或未来工作 |

不单独保存“主要贡献归属”和“推荐阅读模块”。

### 2.1 方法

方法部分只保存一份适度压缩的描述，不维护简略方法和详细方法两套内容。应说明：

- 主要采用什么方法；
- 包含哪些主要步骤或组成部分；
- 各部分如何连接，形成完整处理过程。

方法按照论文实际结构组织，可以分点，但不强制拆成固定数量的模块。论文的核心也可能是整体算法、损失函数或训练策略。完整公式推导、实现参数和其他细节按需从原文读取。

### 2.2 实验概况

实验概况默认说明：

1. 做了哪些实验，例如整体比较、消融、泛化测试或可视化分析；
2. 每类实验验证什么问题；
3. 使用哪些评估指标。

默认不展开全部得分、提升幅度和排名。“验证什么问题”表示实验目的，不自动等于实验已经证明预期结论。用户询问具体效果时，再读取相关原文证据。

### 2.3 结论与局限

简要概括作者的总结，以及作者明确报告的局限和未来工作。未报告的内容不自行补充，也不将未来工作自动改写为已经验证的局限。

## 3. Wiki 渐进式加载

一篇论文只保存一份 Wiki，但分成两个加载区域：

- **入口简介**：研究问题、核心思路；
- **按需正文**：方法、实验概况、结论与局限。

QA 的读取流程为：

```text
读取本次选定论文的全部入口简介
  ↓
判断哪些论文与用户问题相关
  ↓
按需批量加载相关论文的方法、实验或结论
  ↓
必要时读取对应 evidence 原文
  ↓
综合回答
```

具体规则：

- 首次加载的“全部”指本次选定论文集合，不一定是整个资料库；
- 可以一次加载多篇论文的相关部分，不要求逐篇调用；
- 不固定加载次数，已有信息足够即可回答，不足则继续读取；
- 入口没有提到某项内容，不代表论文不存在该内容；
- 用户问题较具体时，QA 可以继续读取正文或 evidence，避免过早排除相关论文；
- 若综述涉及具体方法，QA 需要加载方法正文，不能只根据入口简介宣称已完成深入比较。

| 用户问题 | 主要读取范围 |
| --- | --- |
| 这些论文主要研究什么 | 全部入口简介 |
| 这些论文分别采用什么方法 | 入口简介和相关方法正文 |
| 这些方法如何验证 | 相关实验概况 |
| 某个模块能否用于自己的任务 | 方法正文，必要时补读原文机制、条件和实验 |
| 某项效果具体是多少 | 对应结果、表格及原文证据 |

## 4. Evidence 划分与定位

Evidence 按 MinerU `content_list.json` 中的 `text_level: 2` 划分。

### 4.1 划分规则

1. 遇到一个 `type: text` 且 `text_level: 2` 的 block，开始一个新的 section evidence；
2. 收集该标题和后续所有有效 block；
3. 遇到下一个 `text_level: 2` 标题时结束；
4. 每个二级标题对应一个公开 evidence ID。

一个 section evidence 可以包含：

- 普通正文；
- `5.2.1` 等未被 MinerU 标记为标题层级的小标题和正文；
- 公式；
- 图片 caption 和 footnote；
- 表格 caption、body 和 footnote；
- chart caption 和相关内容。

过滤以下噪声：

- `header`；
- `footer`；
- `page_number`；
- `aside_text`；
- 其他无有效内容的 block。

`text_level: 1` 的论文标题以及作者等信息进入论文元数据。`References` 可以保留原始定位，但默认不作为 Ingest 生成论文内容的依据。

### 4.2 Evidence ID

Evidence ID 使用二级标题起始 block 在原始 `content_list` 中的下标：

```text
{paper_id}:s{content_index:04d}
```

例如：

```text
8272:s0002  → Abstract
8272:s0008  → 1 Introduction
8272:s0064  → 4.2 Personality-Guided Multimodal Interaction Module
8272:s0110  → 5.2 Model Performance
8272:s0121  → 5.3 Ablation Studies
8272:s0138  → 6 Conclusion
```

即使过滤了页眉、页码等 block，ID 仍使用原始数组下标，不进行重新编号。

### 4.3 Evidence 保存内容

每个 section evidence 内部保存：

- evidence ID；
- 二级标题；
- 起止 block index；
- 所包含的原始 block index；
- 起止页码或页码集合；
- 每个 block 的 bbox；
- 文本、公式、表格、图片说明等内容；
- 原始 PDF 与 MinerU 解析版本。

QA 根据一个 evidence ID 直接读取这一整块原文，不需要处理每个 dict 的细粒度 ID。

### 4.4 Wiki 与 Evidence 的关联

Wiki 中每个内容单元保存对应的 `evidence_ids`。通常引用数量为：

| Wiki 内容 | 通常引用数量 |
| --- | ---: |
| 研究问题 | 1–2 个 section evidence |
| 核心思路 | 1–3 个 section evidence |
| 每个方法步骤 | 1 个，必要时 2 个 |
| 每个实验项 | 1 个，跨章节时可增加 |
| 结论与局限 | 1–2 个 section evidence |

同一个 evidence 可以支撑多个 Wiki 内容单元，一个内容单元也可以引用多个 evidence。

## 5. Ingest 的角色与输入

Ingest 不调用工具，也不负责文件写入。本质上是一个受约束的 Chat Client。

Ingest 的职责是：

- 根据宿主提供的论文元数据和 section evidence 生成 Wiki 候选内容；
- 按规定结构输出研究问题、核心思路、方法、实验概况和结论与局限；
- 只能引用宿主提供的 evidence ID；
- 不读取文件、不选择路径、不修改 raw、不直接发布 Wiki。

文件读取、evidence 构造、输出校验、写入和发布均由宿主程序完成。

### 5.1 单次上下文

第一版采用单次输入方式，暂不实现分段读取或读取工具：

1. 程序读取完整 `content_list.json`；
2. 按 `text_level: 2` 整理为 section evidence；
3. 一次性将可用 evidence 提供给 Ingest；
4. 在完整 section evidence 边界计算上下文覆盖范围；
5. 如果完整 evidence 无法全部装入预算，记录总 evidence 数、实际可输入数量、最后可输入位置和截断状态，然后失败关闭。

发生任何截断时不得调用 Ingest、不得生成或发布不完整 Wiki；运行结果必须明确报告输入覆盖不足。第一版不在部分 Evidence 上生成降级 Wiki。

## 6. Review 与发布

Ingest 返回 Wiki 候选内容后，由宿主程序执行：

1. 解析输出；
2. 检查预期字段、数据类型和 evidence ID 是否有效；
3. 执行其他确定性规则校验；
4. 将候选内容、相关 evidence 和实际输入覆盖范围提交给 Review Agent；
5. Review Agent 执行语义审核；
6. 审核拒绝时，将具体问题反馈给 Ingest，重新生成候选内容；
7. 审核允许时，确认 raw 未变化，并确认待发布内容与被审核版本一致；
8. 程序渲染并写入 staging；
9. staging 完整性检查通过后发布。

Review Agent 不直接修改 Wiki，也不负责写文件。它只返回审核结论、具体问题和修改建议。

## 7. 完整流程

```text
检索 Agent 或人工提供 PDF
  ↓
程序校验 PDF、计算哈希、判重并确定 paper_id
  ↓
调用 MinerU
  ↓
校验 content_list.json 存在、可解析且包含有效 block
  ↓
程序读取并标准化全部 content_list
  ↓
按 text_level: 2 划分 section evidence
  ↓
过滤噪声，补充页码、block index、bbox 和来源版本
  ↓
构造单次 Ingest 上下文
  ↓
Ingest 生成 Wiki 候选内容
  ↓
程序解析输出并执行基础结构与确定性校验
  ↓
Review Agent 执行语义审核
  ↓
拒绝 → 将具体问题反馈给 Ingest → 重新生成
  ↓
允许
  ↓
确认 raw 未变化，候选内容与审核版本一致
  ↓
程序渲染并写入 staging
  ↓
执行 staging 完整性检查
  ↓
发布
```

## 8. 组件职责

| 组件 | 职责 |
| --- | --- |
| MinerU | 将 PDF 转换为结构化 `content_list.json` |
| 宿主程序 | 校验来源、构造 section evidence、准备上下文、执行规则校验、写入和发布 |
| Ingest | 根据 evidence 生成 Wiki 候选内容 |
| Review Agent | 在写入前检查候选内容是否受到 evidence 支持 |
| QA Agent | 渐进式读取 Wiki，并根据需要加载完整 section evidence 回答用户问题 |
